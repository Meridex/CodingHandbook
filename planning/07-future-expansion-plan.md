## Expansion Sections

### E-01 — Python Style Guide
**Priority:** High (most group code is Python)
**Suggested location:** `docs/python-style/`
**Responsible:** Maintainer + senior students

Topics to cover:
- PEP 8 compliance (enforced by `ruff` or `flake8`).
- Naming conventions: functions `snake_case`, classes `PascalCase`, constants `UPPER_CASE`.
- Type annotations (Python 3.10+).
- Docstring style: NumPy format (chosen for scientific code).
  ```python
  def effective_potential(phi: float, T: float) -> float:
      """
      Compute the finite-temperature effective potential.

      Parameters
      ----------
      phi : float
          Field value in GeV.
      T : float
          Temperature in GeV.

      Returns
      -------
      float
          Potential value in GeV^4.
      """
  ```
- Import organisation (stdlib → third-party → local).
- Avoiding magic numbers (use named constants or `dataclasses`).
- Using `pathlib` instead of `os.path`.
- Formatting tool: `black` (non-negotiable, no configuration debate).
- Linting tool: `ruff`.
- Pre-commit hook setup.

### E-02 — C++ Style Guide
**Priority:** Medium (some group code is C++)
**Suggested location:** `docs/cpp-style/`
**Responsible:** Maintainer

Topics to cover:
- C++17 as minimum standard.
- Naming: `snake_case` functions, `PascalCase` classes, `kConstant` constants.
- Doxygen comments for public interfaces.
- Header guards vs `#pragma once`.
- RAII and smart pointers.
- Avoid raw arrays; use `std::vector`.
- Compilation flags: `-Wall -Wextra -Wpedantic`.
- Build system: CMake (single choice, no Makefile alternatives).
- Formatter: `clang-format` with a `.clang-format` file in the repository root.

### E-04 — Testing Guide
**Priority:** High
**Suggested location:** `docs/testing/`
**Responsible:** Maintainer

Topics to cover:
- `pytest` basics: fixtures, parametrize, marks.
- Regression test pattern for numerical code:
  ```python
  def test_effective_potential_known_minimum():
      p = EffectivePotential(mu=100.0, lam=0.1)
      assert abs(p.minimum() - 500.0) < 1e-6
  ```
- Testing tolerances in floating-point comparisons.
- When to use `numpy.testing.assert_allclose`.
- Test coverage: what to measure, what not to obsess over.
- `pytest-cov` for coverage reports.
- Mocking external dependencies in tests.
- Performance tests (optional, for computationally expensive functions).

### E-05 — AI-Assisted Development
**Priority:** Medium
**Suggested location:** `docs/ai-tools/`
**Responsible:** Maintainer

Topics to cover:
- How to use GitHub Copilot responsibly in research code.
- Always verify AI-generated numerical code against a known reference.
- AI can help with boilerplate; physics must come from you.
- Code review applies equally to AI-generated code.
- AI for documentation: acceptable with review.
- AI for commit messages: acceptable but check for vagueness.
- Citing AI assistance in papers (field is still evolving — check journal policy).
- Security: never paste credentials, unpublished data, or proprietary algorithms
  into a public AI service.

### E-06 — Reproducible Research Workflow
**Priority:** High
**Suggested location:** `docs/reproducibility/`
**Responsible:** PI + maintainer

Topics to cover:
- The principle: every figure in a paper must be reproducible from a tagged commit.
- Directory structure for a paper project:
  ```text
  paper-project/
  ├── code/          → git submodule pointing to tagged version of solver
  ├── scripts/       → analysis and plotting scripts
  ├── data/          → input data (small) or instructions for large data
  ├── figures/       → output figures (not in Git, generated by scripts)
  └── paper/         → LaTeX source
  ```
- `git submodule` for pinning solver version.
- Environment pinning: `requirements.txt` with exact versions, or `conda-lock`.
- Running the full analysis from scratch: `make all` or a `reproduce.sh` script.
- What to submit to Zenodo: code + scripts + small data, not full simulation output.
- `README` for reproducibility: "To reproduce Figure 3, run: ..."

### E-07 — Release and Publication Workflow
**Priority:** High
**Suggested location:** `docs/release-publication/`
**Responsible:** Maintainer

Topics to cover:
- Full timeline from "paper draft" to "code published":
  1. Feature freeze → final tests → tag `paper/arxiv-submission`.
  2. arXiv submission.
  3. Zenodo deposit → DOI.
  4. Update `CITATION.cff` and README.
  5. GitHub release with release notes.
  6. Repository made public.
  7. Announce.
- Semantic versioning policy for the group.
- CHANGELOG format (keep a changelog conventions).
- What to do when a reviewer asks you to add a feature after submission.

### E-08 — HPC Development
**Priority:** Medium (for students running code on clusters)
**Suggested location:** `docs/hpc/`
**Responsible:** Senior students familiar with the cluster

Topics to cover:
- The HPC is not a development environment — develop locally, run on HPC.
- Never commit HPC job scripts with hardcoded paths.
- SSH key setup for the cluster.
- Cloning the repository on the cluster.
- Submitting jobs with SLURM.
- Saving outputs to a shared storage location (not in the repository).
- Pulling updates to the cluster: `git pull origin main`.
- What to do when the cluster has a different Python/compiler version.

### E-09 — Coding Standards Summary
**Priority:** Low (depends on E-01 and E-02 being done first)
**Suggested location:** `docs/appendices/coding-standards.md`

A one-page summary of all non-negotiable rules:
- Format with `black` (Python) / `clang-format` (C++).
- Lint with `ruff` (Python).
- No hardcoded paths.
- No magic numbers.
- No commented-out code in final commits.
- No `print` debugging in merged code.
